## 3. Security findings

### 3.1 CRITICAL - Broken function-level authorization in RBAC (FIXED)

Every route on the `/admin/rbac/api/*` blueprint was guarded by `@login_required` only, and `services/permission_service.py` performed **no** actor authorization. Any authenticated employee could create roles, grant themselves arbitrary permissions, assign roles to any employee, and delete roles - a direct privilege-escalation path.

Fix: the 13 escalation-vector handlers were switched to `@admin_required` (`routes/roles_permissions.py`). Employee self-service was deliberately preserved:

| Endpoint | Handler | Guard |
| --- | --- | --- |
| `POST /admin/rbac/api/roles` | `api_create_role` | `@admin_required` |
| `PUT /admin/rbac/api/roles/<int:role_id>` | `api_update_role` | `@admin_required` |
| `DELETE /admin/rbac/api/roles/<int:role_id>` | `api_delete_role` | `@admin_required` |
| `POST /admin/rbac/api/permissions` | `api_create_permission` | `@admin_required` |
| `PUT /admin/rbac/api/permissions/<int:perm_id>` | `api_update_permission` | `@admin_required` |
| `POST /admin/rbac/api/assignments` | `api_assign_role` | `@admin_required` |
| `POST /admin/rbac/api/assignments/<int:assignment_id>/revoke` | `api_revoke_role` | `@admin_required` |
| `POST /admin/rbac/api/assignments/bulk` | `api_bulk_assign` | `@admin_required` |
| `POST /admin/rbac/api/delegations` | `api_create_delegation` | `@admin_required` |
| `POST /admin/rbac/api/delegations/<int:dlg_id>/revoke` | `api_revoke_delegation` | `@admin_required` |
| `POST /admin/rbac/api/permission-requests/<int:req_id>/review` | `api_review_request` | `@admin_required` |
| `POST /admin/rbac/api/templates` | `api_create_template` | `@admin_required` |
| `POST /admin/rbac/api/templates/<int:tmpl_id>/apply` | `api_apply_template` | `@admin_required` |

Intentionally left at `@login_required` (would otherwise break employee workflows):

- `POST /admin/rbac/api/permission-requests` (`api_create_request`)
- `POST /admin/rbac/api/permission-check` (`api_permission_check`)
- `POST /admin/rbac/api/permission-matrix` (`api_permission_matrix`)

Verified empirically: employee denied on 13/13, admin reaches 13/13 handlers, self-service unaffected. No test covered these routes, so no test expectations changed.

### 3.2 CSRF - PASS

`core/middleware.py` validates CSRF on every unsafe method, including bodyless mutations. Cookie sessions require `X-CSRFToken`; Bearer-authenticated requests are exempt because they carry no ambient cookie. Probes: 9/9 and 14/14 pass.

### 3.3 Device HMAC - PASS

The 10 device endpoints register through an explicit table, so static decorator analysis cannot see the wrapper; the table was resolved manually. All require device headers, a timestamp within +/-300s, an active device+company row, and compare via `hmac.compare_digest`.

### 3.4 MEDIUM - `pickle.load` in ML model loading (open)

`services/ml_models.py:45` calls `pickle.load(f)`. This is only safe while the model file is a trusted, locally-generated artifact. If the model path is ever writable by another principal, this becomes arbitrary code execution. Recommended follow-up: switch to a non-executable format (JSON weights) or verify a signature before load.

### 3.5 LOW - Input validation returns 500 instead of 400 (open)

Several RBAC handlers raise `AttributeError`/`TypeError` on a malformed or empty JSON body instead of returning a 400. This is an availability/robustness issue, not an authorization bypass, and it predates the fix above. Recommended follow-up: validate request payloads at the `api_guard` boundary.

### 3.6 Informational - review-scanner false positives

The sink scan is heuristic. `eval` hits are string literals inside the frontend security checker, not executed calls. `__import__` uses are fixed-purpose (`datetime`, `platform`). `md5`/`sha1` uses are cache keys and icon hashing, not password hashing. `shell=True`, `os.system`, and unsafe YAML loads: none found.

### 3.7 LOW - RBAC read endpoints still enumerate config to any user (open)

The 17 read-only `/admin/rbac/api/*` routes were intentionally left at `@login_required`, so any authenticated employee can retrieve the full role, permission, assignment, delegation and audit configuration via `GET /admin/rbac/api/roles`, `/permissions`, `/assignments` and `/analytics`. This is configuration disclosure, not privilege escalation, and tightening it would change behaviour for non-admin users, so it was left for an explicit decision. Recommended follow-up: restrict the read routes to admin/auditor roles if that inventory is considered sensitive.
